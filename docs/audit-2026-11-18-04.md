# 18 Nov — fixes applied from the full-day audit

Follow-up to `audit-2026-11-18-03.md`. Two of its three discrepancies were fixable in code;
one is data-blocked. Nothing here changes a trading rule — no entry, exit, cap or pick
threshold moved.

## Fix 1 — one pick window, one confidence

**Audit §5.2.** The same `sector picked 09:45` window spoke with two voices:

```
⏰ LATE LEADER SELL ×6   Market BEAR (81%) …      ← 09:46 digest
⏰ LATE LEADER SELL      Market BEAR (67%) …      ← 09:48 straggler
```

`_catch_up` quotes the pick it ran with, and bot 3 re-derives the pick on **every minute**
(`pick_for(..., projection=True)` rebuilds the forming candle's market), so a name caught on a
later tick carried a number 14 points away from the message above it.

The window now remembers the label and confidence it **opened** with, and every message of
that window quotes them:

* `catchup_due` stores `{"key", "since", "label", "conf"}` when the window opens — on both
  paths that create it (new pick, and the unreadable-`since` repair).
* `_catch_up` overrides the tick's pick with the window's `label`/`conf` before formatting, so
  the digest and the straggler cannot disagree.
* A genuinely **new** window (a different sector or side) takes the new number — that is a
  different pick, and the block for it is sent by the close pass as always.

The number itself is still a projection while the candle is forming; it is just one number per
window now, which is what a reader can check against the block that closes at 09:50.

## Fix 2 — the market block says when it was computed, and on what lag

**Audit §5.1.** Two blocks both stamped `09:45 IST` disagreed on the bear book
(`MET 78 · AUTO 67` vs `MET 85 · DEF 65`) and neither said when it was calculated. The stamp is
the **candle's open**, so a block computed at 09:50:03 from one feed and at 09:50:09 from
another prints the same timestamp and different PERSIST scores.

Two additions, both diagnostic:

1. **Clock.** `format_market(..., sent=…)` appends the compute time:
   `<i>2026-11-18 09:45 IST · calculated 09:45:07</i>`. Both loops pass their own clock
   (`pipeline.run_once`, `scan1m.market_alert`), so a duplicate stamp is now distinguishable at
   a glance. With no clock passed (tests, `--backfill`), the old single stamp is kept unchanged.
2. **Index lag inside the limit.** `SECTOR_MAX_LAG_BARS = 2` means a sector one or two bars
   behind is *legal and used*, and it moves its `persist_bear` with it — invisibly. `run_market`
   now carries `sector_lag = {name: bars}` on the `MarketDecision`, and the block prints the
   non-zero ones, worst first, excluding sectors already named on the `⚠ stale index` line:

   ```
   PERSIST −  CDUR 93 · MET 78 · AUTO 67
   index lag  AUTO 2 · MET 1
   ```

That line is the missing explanation for §5.1: `MET 78` and `MET 85` on two blocks of one
candle are two different *index feeds*, one of them a bar behind — not two different rules.

## What is still open, and why no code was written for it

**The numbers in §5.1 themselves.** Both loops are provably aligned to the closed decision bar
(`m5 = {sym: df.loc[df.index <= last]}` in `pipeline.run_once`, the identical slice in
`scan1m._own_market`), and `run_market` is the same function in both. With identical inputs the
persist scores must be identical, so the difference came from the *data* — a sector index that
had published one bar fewer at one of the two run times. Nothing in the code is wrong to fix;
what was missing was the disclosure, which Fix 2 adds. One more day of blocks settles it: the
`index lag` line will name the sector and the bars.

**Audit §5.3 (breadth improved while conf rose).** `_dir_conf` has no breadth leg — it is MTF
(35) + consecutive closes below VWAP (25) + ADX (25) + |npos−50|·0.3, ±5/−2 for the OR break.
Adding breadth would be a **pick rule change**, and on 18 Nov it would have *lowered* the bear
score while the tape fell — the opposite of what the day wanted. Left alone deliberately.

**The late entry** (audit-02) stays parked: it needs a replay over 12–17 Nov, not another
alert.
