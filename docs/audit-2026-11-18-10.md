# 18 Nov — the 1m bot's own log (run #91, 08:30–11:21 IST)

The log of the 1m scanner was the one file this audit could not see: `gh` cannot download it
(`results-receiver … EOF`), so it was read from the owner's upload. It covers the whole morning
session up to the 11:21 handover — 2 h 51 m of scanning, guard clean ("no other 1m run active —
this run becomes the loop").

The morning itself was quiet and correct: **two projections, seven LATE LEADER catch-ups, no
entries** — the market was WAIT from 09:55 to 10:15 and BEAR-but-under-confidence either side of
it, so bot 1 took nothing either. What the log did expose is that bot 3 loses alerts in the same
two ways bot 1 did, plus a third that is its own.

## Finding 1 — an entry alert Telegram refused was never re-sent

```
10:20:09 WARNING telegram: telegram bot3 send failed: 400 … Unsupported start tag "" at byte offset 426
10:20:13 ERROR   telegram: telegram bot3 delivery failed: …
10:20:13 WARNING scan1m:   bot 3 delivery failed for LGEINDIA; the next minute retries
10:21:12 WARNING scan1m:   bot 3 delivery failed for LGEINDIA; the next minute retries
10:21:15 INFO    scan1m:   1m projection for LGEINDIA did not hold (did not hold) — no message
```

The projection itself had been delivered at **10:16:06** (`LGEINDIA SELL @ 1714.80`). Its
**close confirmation** — the message that would have said confirmed or cancelled — bounced twice
and then the projection was written off as "did not hold". No entry was recorded, no position was
opened, and the only trace was three lines in the log.

The retry was never a retry: `tick` re-runs a candle only while a **feed** has not published
(`_retry_pending`). This candle's feeds were complete — it was re-run on the next minute only
because *two other* feeds had lagged. When every feed is on time, a refused entry alert becomes a
lost entry, while the log says the opposite.

Now the refusal is booked and the candle stays owed until the alert deadline:

* `st["undelivered"]` remembers the name, its candle, the first refusal and the number of tries;
* the candle is **not marked judged**, so `tick` returns `retry` on the next minute and the entry
  is genuinely re-sent (verified by a test);
* the projection is filed as `undelivered`, not `cancelled`, so the summary cannot call a delivery
  failure a lost signal;
* the day's summary names what never arrived:

```
⚠ entry alert(s) not delivered: 1 — LGEINDIA 10:15 (2 tries) — Telegram refused them,
  so no entry was recorded and no trade is being tracked
```

The markup cause of this particular refusal is already gone (`telegram.esc` + the plain-text
fallback, #46); this fix covers every other way a send can fail — an outage, a rate limit, a
token that stopped working at 10:20.

## Finding 2 — eleven messages lost to the same `<`, on bot 3

33 failed sends for **11 messages** at `09:20, 09:25, 09:30, 09:35, 09:40, 09:45, 10:05, 10:10,
10:15, 10:20, 10:21` — same error, same cause (`conf {n} < {PICK_MIN_CONF}` in the 5m block bot 3
shares with bot 1) and the same fix already merged in #46. `send_bot3` goes through `_send_to`,
so bot 3 gets both the escape and the plain-text fallback.

## Finding 3 — half the log was one sentence, printed per name per minute

479 of the 949 body lines said *"1m <NAME>: last SELL fire was <time>, not this candle — not
projected"* — one line per name per minute, eight names, all morning. Likewise *"no sector pick to
project on"* printed four times per candle (38 lines for 10 candles).

Both are now one line:

```
1m 10:20: 8 names fired on an earlier candle, not this one — not projected:
  CROMPTON 09:25, DIXON 09:25, HAVELLS 09:25, KALYANKJIL 09:20, LGEINDIA 10:15, …
1m 09:55: no sector pick to project on — nothing projected (projected from the forming candle)
```

Nothing is lost — the same names and times — and the log becomes readable: roughly 700 lines
instead of 970 for the same morning.
